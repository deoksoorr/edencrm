## 1. 조회 전용 원칙

- 보드에서 **단계를 직접 바꾸는 모든 기능이 제거**되었습니다: 카드 드래그 이동, 카드 빠른 수정(드로어), AJAX 보드 갱신.
  화면 숨김이 아니라 서버 라우트 자체를 제거해 주소로 직접 호출해도 404 입니다(QA 실측: GET·POST 전 조합 404).
- 유지되는 것(원본 데이터 관리): 카드 클릭 → **상세 페이지**, [수정](등록·수정 폼), [삭제], [+ 신규 영업기회].
  기존 12단계 값(stage_id)은 수정 폼에서만 변경할 수 있고, 삭제되지 않고 산정 입력·이력으로 유지됩니다.
- 이유: 계약·견적의 실제 상태와 보드 단계가 어긋나는 사례가 실데이터에서 확인됨(진행 계약인데 '견적발송' 잔존, 파기 계약인데 '계약대기'
  잔존 → 예상 금액 과대). 표시 단계를 원본에서 **자동 산정**하면 이 불일치가 구조적으로 사라집니다.
- 화면 명시 문구: 「단계는 원본 데이터(계약·견적·리드 단계) 기준 자동 산정 — 조회 전용」.

## 2. 7그룹 정의와 우선순위

| 그룹 키 | 화면 라벨 | 의미 |
|---|---|---|
| new_inquiry | **신규 문의** | 막 들어온 문의 — 다른 신호 없음 |
| consulting | **상담 중** | 상담 예약·진행 |
| site_check | **현장 확인** | 현장 실측 단계 |
| quoting | **견적 진행** | 견적 작성~계약 대기(체결 전) |
| contracted | **계약** | 계약 체결(진행·보류·완료 계약 연결 또는 계약완료 리드) |
| on_hold | **보류** | 고객 사정 등으로 잠정 중지 |
| closed | **종료** | 실주·취소·연결 계약 파기 |

여러 신호에 동시 해당하면 **우선순위: 종료 > 보류 > 계약 > 견적 진행 > 현장 확인 > 상담 중 > 신규 문의** 로 단 하나만 정합니다.
충돌 해석 규칙: 보류 단계 리드에 진행 계약이 연결돼 있어도 **보류**(전역 우선순위 준수), 종료 신호는 항상 최우선,
리드에 여러 계약이 걸리면 진행군 > 종결군 순으로 해석.

## 3. 산정 신호 (강한 것부터)

1. **직접 연결 계약** (리드→견적→계약 연결 사슬): 파기/취소 계약 → **종료**, 진행/보류/완료 계약 → **계약**
2. **유효 견적** (리드에 연결된 견적, 임시저장 제외) → **견적 진행** 이상
3. **고객 단위 보조 신호 (추정 — 표시 전용)**: 그 고객의 영업 기회가 **1건뿐**일 때만(딜 혼동 배제) —
   리드 등록 **이후** 성립한 진행군 계약 → 계약 추정 / 진행 계약이 없고 리드 등록 이후 파기·취소 확정 → 종료 추정.
   계약이 리드보다 **먼저** 성립한 경우(시기 역방향)는 별개 딜 가능성으로 추정하지 않음.
   추정 근거 카드에는 「계약 C번호**·추정**」으로 표기되고, 배지 마우스오버에 산정 근거가 나옵니다("자동 산정: ...").
4. **12단계 fallback 매핑표** — 위 원본 증거가 없을 때 리드의 기존 12단계 값을 그룹으로 매핑:

| 12단계(등록 순서) | → 7그룹 | 비고 |
|---|---|---|
| 신규문의 | 신규 문의 | |
| 상담예약 | 상담 중 | |
| 현장실측 | 현장 확인 | |
| 견적작성 · 견적발송 · 협상중 · **계약대기** | 견적 진행 | 계약대기는 체결 전이므로 '계약' 아님 |
| 계약완료 | 계약 | |
| 보류 | 보류 | |
| **장기미응답** | **보류 (잠정)** | **정책 미확정(P-4)** — 보류 vs 상담 중 귀속 확인 필요. 현 데이터 0건 |
| 실주 · 취소 | 종료 | |

**일정·활동 신호는 사용하지 않습니다** — 현 데이터 구조상 활동 기록(customer_activities)에 리드 연결 컬럼이 없고,
일정(schedules)도 프로젝트 연결뿐이라 상담 중·현장 확인 그룹은 **구조적으로 12단계 fallback 전용**입니다(임의 추정 금지 원칙).

### 시드 데이터 실측 예 (QA 확인)

- 판교 리드(12단계 '계약대기') → **종료** 컬럼: 같은 고객의 파기 계약 추정 — 진행 예상 금액에서 3,300만 원이 제외되어 KPI 부풀림 해소.
- 서초 리드(12단계 '견적발송') → **계약** 컬럼: 같은 고객의 진행 계약(고객 단위 단독 리드) 추정.
- 한빛 리드는 계약이 리드보다 선행 → 추정하지 않고 12단계 값대로 '현장 확인' 유지(시기 역방향 규칙).

## 4. 정합성 규칙

- 표시 단계는 **파생값**이므로 저장·보정이 필요 없습니다 — 원본(계약·견적·리드)이 바뀌면 다음 조회에서 자동 반영되고,
  같은 데이터로 몇 번을 조회해도 같은 결과가 나옵니다(QA: 연속 조회 결과 동일 확인).
- 리드 원본의 연결 누락(계약→리드 연결 0건 등)은 자동 수정하지 않습니다 — 금액 불일치(예: 리드 예상 4,200만 vs 계약 1,540만)로
  동일 딜을 데이터만으로 단정할 수 없기 때문입니다. 아래 dry-run 리포트로 후보만 확인합니다.
- 상단 요약 4종(진행 예상 금액/견적 진행 금액/계약 전환/보류·종료)은 파생 그룹 기준으로 집계되며 기간·담당·검색 필터와 연동됩니다.
  '진행 예상 금액'은 종료·보류·계약 그룹을 제외한 진행 그룹(신규 문의~견적 진행)의 예상 계약 금액 합입니다.
- 카드의 '다음 일정'은 다음 연락 예정일 기준이며, 지난 날짜는 지연 표시됩니다.

## 5. 리드-계약 연결 후보 dry-run 절차

연결 누락을 정리하고 싶을 때(관리자·개발 담당):

```bash
php scripts/lead_link_candidates.php     # 읽기 전용 — DB 를 절대 변경하지 않음
```

- 휴리스틱: 동일 고객 + 계약 성립/파기 시점이 리드 등록 이후(금액 비율은 참고 표시) / 견적 lead_id 백필 후보는 동일 고객 + 견적 작성일 ≥ 리드 등록일.
- 현 시드 기준 출력: 리드↔계약 후보 3건 + 견적 백필 후보 1건.
- **확정 연결(UPDATE)은 하지 않습니다** — 후보 리포트를 보고 실제 같은 딜인지 사람이 판단한 뒤, 사용자 승인 후 별도 작업으로 진행합니다(**정책 미확정 P-2**).

## 6. 기간 필터 규약 (레거시 호환)

- 파이프라인 기간 필터는 공통 컴포넌트(프리셋 7종)를 쓰며 견적·계약과 동일 날짜 경계입니다([PRODUCT_MANUAL 2번](PRODUCT_MANUAL.md#2-공통-기간-필터-사용법)).
- 옛 주소의 기간 값은 자동 변환됩니다: `7d/30d/90d` → 같은 경계의 직접 지정(오늘−n일부터), `month` → 이번 달.
  변환 규칙은 R5 에서 레거시 키 유입이 없음을 확인한 뒤 제거될 예정입니다(북마크 구제용).
- 기준 select: 등록일(기본) / 최근 연락일(연락 기록 없는 리드 제외).
